## Esecuzione concreta da implementare

- Una run/cell-family gestisce un solo N e modo docs/code/mixed in un processo fresco. CLI per checkout dedicato, output nuovo, N, modo, k-list, repeats (default5). PM avvierà 9 famiglie N=10,30,100 × docs/code/mixed, k=0,1,10 e100 solo N100. N è totale file eleggibili, misto metà docs/metà code; k1 misto modifica un doc, k10 metà/metà. Rifiuto k>N esplicito, niente successo/skip mascherato.
- Checkout sperimentale `rag/eval/results/<run>/sandbox/experiment` e database al suo interno; radice canonical verificata contro repo/results prima di ogni mutazione, niente link/reparse escape. Nome collection prefisso strettamente dedicato `sidecar_0628_...`, Qdrant fisso localhost16333, server solo localhost18000. Config effettiva e core paths devono coincidere, NO import di core del checkout operativo. Un argomento arbitrario che si autodefinisce sandbox non basta. Un child subprocess che esegue script nel checkout dedicato è preferibile a reload/modifiche di sys.modules.
- Corpus sintetico deterministico, file brevi e stessa distribuzione di lunghezze fra N. Markdown indicizzabile con parola VarianteA→VarianteB, codice modifica corpo/docstring reale analizzata, sempre byte length invariata (non riscrivere newline). Manifest dei file/hash/byte, token disponibili e conteggi baseline. Nessuna modifica corpus operativi.
- Server reale HTTP embedded nello stesso processo per reload controllato, come driver F1; bootstrap tramite job incrementale HTTP su database/collection vuoti, registrare job_id e fingerprint. Nessun full rebuild/gate e nessun /ask. Controllare integrità e assenza stale.
- Congelare baseline file E indice: artefatti/manifest/CURRENT e punti Qdrant. Riutilizzare snapshot nativo Qdrant (`create_snapshot(wait=True)`, `recover_snapshot(location='file:///qdrant/snapshots/<collection>/<name>', priority='snapshot', wait=True)`), verificando contratto installedclient. Snapshot dentro server, non path Windows. Non usare solo rollback CURRENT: delta modifica Qdrant in place.
- Prima/dopo OGNI campione e in finally: attendere writer, interrompere/join query di contesa, ripristinare byte sorgenti e artefatti della baseline sotto writer lock, recuperare snapshot Qdrant, reload e controllare fingerprint, CURRENT, integrità e punti (digest paginato ID/payload/vettori o verifica equivalente forte). Non cancellare file con lettori/writer attivi. Backup fuori db, preservare logs/output. Proteggere tutte rimozioni con verifiche canonical; nessuna pulizia generica sandbox. Se restore fallisce run invalida, arresto sicuro, evidenze conservate.
- Mutare k file distinti esistenti, verificare hash e lunghezza. Verificare job completed+reload completed/token nonnull (fase3 potrà aggiungere noop skipped contratto), noncoalesced/nonstale, per docs planned.modified esatto/reindexed_docs, per code counts.code_modified esatto, chunks/token effettivi per doc. Token codice null con motivo già core: non inventarli; registrare byte e simboli/code hash prova lavoro reale.
- 5 ripetizioni per cella, no-op abbinato per rep, tempi journal coda/lock/build/reload/readiness e breakdown, eventi assoluti monotoni per correlare sampler esterno. Query HTTP durante reindex da UN reader concorrente (stesso pattern su tutte celle) con risultati/latenze/errori e query baseline senza contesa. Pausa breve tra query per non creare flood; pattern esplicito nei parametri. Nessun generatore LLM.
- JSON incrementale/checkpoint dopo ogni campione anche invalido, exit nonzero su errori. SIGINT/TERM/BREAK stop al prossimo confine sicuro, mai exit lasciando job attivo. Server/writer/query joined prima di restore/shutdown finale. Nessun kill automatico.
- CSV/tabella mediana/min/max per cella e differenza abbinata T(N,k)-T(N,0); no p95 stabile da5, differenza NON soloembedding. Grafico e aggregazione multiN possono essere PM dopo run, non necessari nel worker.

## Test essenziali

Guard rifiuta checkout/collection/path non dedicati PRIMA scritture; falsa noop, k10 file distinti/byte lunghezza, k>N, journal incompleto/coalesced invalido, restore anche su eccezione con dati iniziali verificati (non soltanto chiamata mock), code/mixed conteggi. Red/green per le diramazioni nuove. Nessuna suite che finga misure prestazionali. Report cosa è implementato/testato e cosa richiede run reale.

## Limiti

Sampler esterno cattura processo/server e Qdrant durante run; non serve una seconda libreria. Cache OS non controllata, CPU quattro thread e modello offline invariati. Lo snapshot non deve essere preso/recuperato durante writer. I/O restore fuori intervallo misurato ma dichiarato. Incertezza o blocco concreto: comunicare PM, non costruire workaround che falsi confronto. Il ramo full crossover non è aperto: non dichiararne il risultato.
